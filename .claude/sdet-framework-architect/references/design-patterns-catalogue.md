# Design-pattern catalogue for test-automation frameworks

Patterns that recur in well-built automation frameworks. Each entry: what it is generically, where it earns
its place in a test-automation context, and the SOLID/clean-code principle it primarily serves. Treat this as a
lookup table — when a piece of framework code feels ad hoc, check whether it's secretly one of these and name it.

| Pattern | Generic definition | Where it earns its place in test automation | Principle served |
|---|---|---|---|
| **Adapter** | Wrap a third-party API behind a class the rest of your code depends on. | Every element/control class wrapping the underlying driver's locator/selector API. Isolates the blast radius of a driver/tool upgrade or swap to one layer. | Dependency Inversion / low coupling |
| **Template Method** | Base class fixes an invariant algorithm skeleton; subclasses fill in the variable steps. | Element constructors (fixed behavior, variable "how do I find myself"); API service base class (fixed request lifecycle, variable endpoint/verb/body). Guarantees a cross-cutting guard (auth injection, logging, error handling) can't be silently skipped by a new subclass. | Open/Closed, DRY |
| **Strategy (by configuration)** | Interchangeable algorithms/behaviors selected behind one interface, often via a small config object rather than separate subclasses. | An element resolving id-vs-label-vs-index lookup strategy from a constructor options object. | Open/Closed |
| **Composition over inheritance** | Build a complex object from smaller collaborator objects rather than deep subclassing. | A dropdown composing a trigger element + an options-list element; a page composing header/main/footer containers; a service composing a nested child service. Default choice whenever "is-a" doesn't cleanly hold. | Single Responsibility, Liskov substitution safety |
| **Facade** | One simplified interface hiding a multi-step subsystem. | A page/screen object exposing `signIn(email, pw)` instead of making callers sequence raw element interactions; a `send()` method on a service hiding URL-building/auth/parsing. | Encapsulation, low coupling |
| **Composite** | Treat a group of objects and a single object through a uniform interface; part-whole hierarchies. | A page object composed of containers composed of elements, queried/asserted on at any level uniformly. | Single Responsibility per part |
| **Observer (pub/sub)** | Producers publish events; independent consumers subscribe without the producer knowing about them. | CI test-result reporting fanning out to multiple notification channels (Slack/Teams/email/webhook) — adding a channel never touches the producer. Fault-isolate each subscriber (e.g. run all subscribers concurrently and let each fail independently) so one broken integration doesn't break the others. | Open/Closed, fault isolation |
| **Factory Method** | Centralize how instances of something are constructed, optionally caching/memoizing. | A form/composite component vending already-scoped input/button instances, memoized by a canonical key so repeated requests for "the same" field return one instance. A container exposing a factory method (not a cached singleton) for each dynamically-repeated region. | DRY, correct object lifetime |
| **Dependency Injection / IoC** | Objects declare what they need; a composition root supplies concrete instances. | The fixtures/composition-root layer: tests declare "I need `signInPage`" and receive a fully-wired instance without constructing it themselves. | Dependency Inversion |
| **Controller/Service layer** | One class per external resource/endpoint group, mirroring the API's own structure. | The API service layer — one service class per controller/tag, one method per endpoint. | Single Responsibility |
| **Chain of Responsibility (state lookup)** | A request for a value walks up a chain of linked objects until one resolves it. | A child API service's `token`/header lookup delegating up through its `parent` reference so nested resources inherit auth without redeclaring it. | DRY, encapsulation |
| **Prototype / fluent clone** | Return a modified copy of `this` (preserving the actual runtime subtype) instead of mutating in place. | Fluent, chainable element-narrowing methods (`withText(...)`, `withIndex(...)`) that must work correctly across an entire subclass tree. | Immutability, Liskov substitution |
| **Fluent interface** | Chainable configuration methods that read like a mini-DSL. | Multi-step element/query configuration (`table.withParentLocator(...).getRowWithData(...)`), reducing setup boilerplate at call sites. | Readability / KISS |
| **Command** | Encapsulate a multi-step operation as one reusable, named call. | A page-object business method (`signIn`, `checkout`) hiding the sequence of underlying element interactions — exposes "what", hides "how". | Encapsulation |
| **Role-based interface segregation** | Split one fat capability surface into smaller role interfaces/branches (e.g. "clickable" vs "editable") instead of one base class with every possible action. | An element base-class hierarchy where a link only gets click/hover behavior and an input only gets fill/clear behavior, never a shared grab-bag of both. | Interface Segregation |
| **Object Pool + RAII/bracket leasing** | A bounded pool of a limited, stateful, shared resource, issued as a scoped/closeable handle so release happens deterministically — even on failure — instead of relying on the caller to remember cleanup. | A pool of shared test accounts/licenses/hardware rigs that can't be freshly created per test (too slow, or externally rate-limited) but must never be used by two concurrently-running tests at once. A test acquires a lease via a `try`-with-resources/`using`/`with`-style block; the pool blocks or errors if exhausted rather than silently oversubscribing. | Encapsulation, guaranteed cleanup (the "own your data" principle applied to a *leased*, not owned, resource) |
| **Repository / interface-impl separation** | Define a capability as an interface; exactly one class implements it and is the only place that knows the underlying mechanics (e.g. locators). Every other caller depends on the interface type. | A page/screen object declared as an interface (`LoginPage`) with one `LoginPageImpl` holding all its locators — a stricter, one-step-further application of the Container/Screen layer's Facade than a plain concrete class, useful when a team wants the compiler to enforce that no caller ever reaches past the interface. | Dependency Inversion, Interface Segregation |

**Using this table when reviewing code:** if you see a class doing two unrelated things, ask which composition/
extraction pattern above would split it. If you see the same setup logic duplicated across call sites, ask whether
a Factory Method or Facade would centralize it. If you see a new integration requiring an edit to existing dispatch
code, ask whether an Observer/pub-sub restructuring would make it additive instead.
